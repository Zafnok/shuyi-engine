# 3435 — The MCP server speaks protocol 2026-07-28

## Context

Anthropic's article *Skills over MCP, tasks and more* (2026-11-24,
`claude.com/resources/articles/skills-over-mcp-tasks-and-more`) puts
three MCP features in Claude and Claude Code: skills served by an MCP
server (public beta), tasks, and elicitation. All three need MCP
revision **2026-07-28** on the connection. Claude Code's MCP docs
(`code.claude.com/docs/en/mcp`, read 2026-11-26) say so for skills
("MCP revision 2026-07-28 or later") and for tasks ("connections on
revision 2026-07-28 only"); the skills extension's spec
(`github.com/modelcontextprotocol/ext-skills`,
`specification/beta/skills.mdx`) is "written against base protocol
revision 2026-07-28" and declares the extension "in `server/discover`"
only. Claude Code v2 asks a server whether it speaks 2026-07-28 and
uses it if so; any other server connects on the old protocol.

Our server speaks only the old ones:
`crates/cli/src/mcp/server.rs` has `PROTOCOL_VERSIONS = ["2025-06-18",
"2025-11-25", "2025-03-26", "2024-11-05"]` (about line 32), and its
`initialize` (about line 776) answers the first when the client asks for
none it knows. So 3434 (skills), 3436 (tasks) and 3437 (elicitation)
all wait on this ticket.

What 2026-07-28 changes, from its changelog
(`modelcontextprotocol.io/specification/2026-07-28/changelog`) and
`server/discover` page. Read both again when you start: this list was
taken on 2026-11-26.

- **No handshake.** `initialize` and `notifications/initialized` are
  gone. Every request carries `params._meta` with
  `io.modelcontextprotocol/protocolVersion`,
  `io.modelcontextprotocol/clientCapabilities` and (SHOULD)
  `io.modelcontextprotocol/clientInfo`. An unknown version is
  `UnsupportedProtocolVersionError` (`-32022`). Results SHOULD carry
  `_meta["io.modelcontextprotocol/serverInfo"]`.
- **`server/discover`** (servers MUST implement it): answers
  `resultType: "complete"`, `supportedVersions`, `capabilities` (now
  with an `extensions` field), `instructions`, `ttlMs` and
  `cacheScope`. A client speaking both generations over stdio SHOULD
  send it first as its probe, so a server that answers it is taken as a
  2026-07-28 server.
- **`resultType`** on every result: `"complete"` or `"input_required"`.
  `ttlMs` and `cacheScope` (`"public"` or `"private"`) are required on
  `server/discover`, `tools/list`, `resources/list`, `resources/read`
  (and the prompts' and templates' lists, which we don't serve).
- **No server-initiated requests.** `roots/list` is no longer one
  (Roots are deprecated, SEP-2577, not removed). The multi-round-trip
  pattern (SEP-2322) replaces it: the server answers
  `resultType: "input_required"` with `inputRequests`, and the client
  sends the same request again with `inputResponses`.
  `notifications/roots/list_changed`, `ping` and `logging/setLevel` are
  removed.
- **List changes** come through `subscriptions/listen`: the client opts
  in to `toolsListChanged` (and others), and each notification carries
  `io.modelcontextprotocol/subscriptionId`.
- **Resource not found** is `-32602` (SEP-2164), not `-32002`.
- **No protocol sessions.** State across calls is server-minted handles
  passed as tool arguments (SEP-2567).

Two of our designs lean on what went away:

- [ADR-0035](../../docs/adr/0035-the-mcp-server-follows-the-sessions-folder-roots-a-forwarded-server-per-workspace-and-a-restart-when-the-engine-moves.md)
  §1: the session's folder is the first root, asked for by the server's
  own `roots/list` (id `ROOTS`, `"shuyi-roots"`) after
  `notifications/initialized`, and again on
  `notifications/roots/list_changed` (2546, 2547). `Server::rooted`
  takes the answer.
- ADR-0035 §4: `notifications/tools/list_changed` when the session
  folder's forwarded server lists other tools (`Server::poll`).

The session tools (`start` … `stop`, ADR-0031) keep one headless game
per server process. On stdio that is still one client per process, so
the session stays the process's; no handle is needed. Say so in the ADR.

Codex and older Claude Code keep the old protocol, so both generations
are served by one server.

## Scope

**In:**
- **Both generations.** A request whose `params._meta` holds
  `io.modelcontextprotocol/protocolVersion` is answered by the 2026-07-28
  rules; `initialize` and a request without it, by today's. `"2026-07-28"`
  joins the known versions as the newest. A version in `_meta` the
  server doesn't know is `-32022` with the supported versions in `data`.
- **`server/discover`**: `supportedVersions` (2026-07-28 only: the old
  ones are reached by `initialize`), `capabilities` (`tools` and, when
  3434 lands, `resources` and `extensions`), `instructions`
  (`INSTRUCTIONS`), `serverInfo` in `_meta`, `ttlMs` and
  `cacheScope: "public"`.
- **Each result** on a 2026-07-28 request carries `resultType` and
  `serverInfo`; `tools/list` carries `ttlMs` and `cacheScope`, in
  `Op::ALL` order then `Op::SESSION`'s (already deterministic: a test
  says so).
- **The session's folder** on 2026-07-28: the first `tools/call` (or
  `tools/list`) of a client that declared `roots` in its
  `clientCapabilities` and hasn't given its roots yet is answered
  `resultType: "input_required"` with one `inputRequests` entry asking
  `roots/list`; the retried request's `inputResponses` carries the
  roots, and the server takes them as `rooted` does today, then answers
  the call. Read SEP-2322 for the exact field names and the request
  state it requires. A client without `roots` resolves against the
  server's folder, as today. Decide (and write in the ADR) whether to
  ask again on a later call; there is no `list_changed` to say when.
- **The tool list follows** through `subscriptions/listen` when the
  client opted in to `toolsListChanged`; otherwise the old notification
  on the old protocol only.
- **Forwarding** (ADR-0035 §2): a forwarded server is started and asked
  in the protocol of the call it answers. The simplest that holds: the
  parent speaks the old protocol to it whatever the client speaks, and
  maps the answer (adding `resultType`, `serverInfo`, the cache fields).
  If a forwarded server is an older `shuyi` with no 2026-07-28, that is
  then no problem. Record the choice.
- **An ADR** (the `write-adr` skill), amending ADR-0035 §1 and §4: the
  two generations, the folder by `input_required`, list changes by
  subscription, the session kept per process.
- **Docs:** `docs/contract.md`'s *The MCP server* (the protocols it
  speaks); `crates/cli/src/mcp/server.rs`'s module docs; the book's
  *Tools for agents* (one sentence: which clients get which protocol).
- No public type changes shape: `PROTOCOL_VERSIONS` is `pub`, so if its
  length changes the `api` job finds it; write the `Breaking:` line
  then, or make it a slice.
- **Estimated size:** about 1,200 lines (code 550, tests 500, docs 150).
- **Split:** past 900 lines, split off the forwarding (a forwarded
  server's answer mapped for a 2026-07-28 client) into a new ticket,
  with forwarded calls on a 2026-07-28 connection answered `SH3005`
  "this protocol is not forwarded yet" until then.

**Out (do not do):**
- Serving skills (the skills extension) and resources: 3434.
- Tasks (the tasks extension): 3436.
- Elicitation: 3437.
- Streamable HTTP and its headers (`Mcp-Method`, `Mcp-Name`): the
  server is stdio only (ADR-0031).
- Dropping the old protocol.
- The first-contact build time before the server can answer at all:
  3414's.

## Completion notes

**What was done.** `crates/cli/src/mcp/server.rs` serves both
generations, chosen per request (ADR-0156): a request with no
`io.modelcontextprotocol/protocolVersion` in `params._meta`, and
`initialize`, go to `of_old`, unchanged; `"2026-07-28"` (`STATELESS`)
to `of_stateless`: `server/discover`, `tools/list` (with `ttlMs` and
`cacheScope`), `tools/call` and `subscriptions/listen`, each result
through `of_2026` (`resultType` and `serverInfo`); another version is
`-32022` with `data: { supported: ["2026-07-28"], requested }`. The
folder comes by `input_required` on the first `tools/call` of a client
with `roots`, once per process. The tools' changes go on each
subscription that asked for `toolsListChanged`, and the old
notification only to a client that said `initialize`. A forwarded
server is still spoken to on the old protocol, and its answers are
mapped. The handlers build messages as `Value`s; `handle` and `poll`
keep their signatures. Six tests in `server/tests.rs`; the old tests
pass unchanged. Docs: `docs/contract.md`'s *The MCP server*, the
module's docs, the book's *Tools for agents*; ADR-0156 amends ADR-0035
§1 and §4 and extends ADR-0031. 3434, 3436 and 3437 got a **From 3435
(done)** note naming what now exists.

**Deviations.**

- **`PROTOCOL_VERSIONS` is unchanged.** 2026-07-28 is its own
  `pub(crate) const STATELESS`, not a fifth entry: `initialize` answers
  the list's first to a client asking for a version it doesn't know, and
  the forwarded servers are started on it, so 2026-07-28 there would
  answer, and ask, a handshake that version doesn't have. No public item
  changes (ADR-0156, *Alternatives*).
- **`tools/list` never asks for the roots**, only `tools/call` does:
  the specification allows `input_required` only on `tools/call`,
  `resources/read` and `prompts/get`.
- **`ttlMs` and `cacheScope` on `tools/list`** are `0` and `"private"`
  when the server forwards (its list follows the session's folder),
  `3600000` and `"public"` when it doesn't; `server/discover` is
  `3600000` and `"public"`.
- **A missing `clientCapabilities` is read as `{}`**, not refused with
  `-32602`.
- No split: the PR stayed under the ticket's 900-line split point.
