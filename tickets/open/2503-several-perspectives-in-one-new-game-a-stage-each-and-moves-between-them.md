# 2503 — Several perspectives in one new game

## Context

Nick, 2026-10-17 (`docs/decisions.md`): a game "can be both (i.e.
transition between them) so let player tick off multiple". The wizard
(2502) lets a developer pick several perspectives, but until this ticket
each becomes a separate stage with nothing joining them.

[ADR-0013](../../docs/adr/0013-starting-a-game-a-wizard-over-the-catalog-and-templates-made-of-parts.md)
§4 sets the rule. A stage per perspective (ADR-0003 §1), generic over its
marker (ADR-0009 §3). A flow screen that moves between them. The move
part of a perspective that has a move guide (ADR-0009 §5), or a plain
door on the `travel` action where no guide exists yet.

At the time this ticket is likely worked, only `top-down-grid` is ready.
The other perspectives are parked (1122, 1126, 1127). So this ticket
builds the mechanism and proves it with **fixture perspectives** in
`shuyi-cli`'s tests. Each perspective ticket adds its own part when it
lands (their scopes say so). If some of them are already done when this
is worked, add their parts here too: `stage-top-down` (1122),
`stage-isometric` (1126), `stage-side-view` (1127), and the move
`top-down → top-down-grid` (1125).

## Scope

**In:**
- **From 2501 (done):** the composer generates
  `crates/game/src/stages.rs` (`template::stages_rs`) from one stage:
  `names()`, `Own` (that stage's `Own`, `BasicData`'s own part),
  `own`, `first`, `screens` and `tools()`, each stage a module
  `stages/<id with _>.rs` (`docs/templates.md`, ADR-0042 §2). It
  refuses a second stage (`ComposeError::Stage`). This ticket lifts
  that: `Own` becomes a struct with each stage's part, which each
  stage's module reaches by its own field, `first` and `tools` take
  the stage picked, and the base part's title, which starts the first
  stage today, lists them. The base part's tests hold for every game
  the template makes (the title first), and keep doing so.
- **The flow in the base part** (2501's `templates/shuyi-default/base`):
  - `src/stages.rs` (generated by the composer from every part's
    `stage`) lists the stages in the order picked;
  - the flow screen starts in the first stage and owns what crosses
    between stages (ADR-0003 §1). The template keeps one small shared
    struct, `Carry { from: StageId }`, so the pattern is visible; the
    developer grows it.
- **Moves** in `template.ron`: a part may declare `moves: [Move { from,
  to, files }]`. The composer, for each ordered pair of picked
  perspectives (first to second, second to third, and back):
  - uses the declared move's files, if one part declares that pair;
  - otherwise uses the base part's **door**: in the `from` stage, the
    action `travel` (added to the game's `ActionSet`, bound in its
    default keymap, never a hard-coded key: the `input-actions` skill)
    asks the flow to go to the next stage, and in the last stage it goes
    back to the first;
  - two parts declaring the same pair is `ComposeError::SameMove`.
- **The new game's README** lists the stages and each move, and says
  for each door "this move has no guide yet" with a link.
  **Either order with 2004:** if 2004 is done, the link goes to
  `docs/guides/README.md`; if not, to ADR-0009 §5, and 2004 points it
  at `docs/guides/README.md`.
- **The new game's test**, `tests/moves.rs`, generated: a Harness test
  that starts the game, crosses every move in order with the actions the
  move needs (for a door, `travel`), and checks the top screen after
  each. A move part supplies its own steps in its `files`, as
  `tests/moves/<from>-to-<to>.rs`.
- **Fixtures** in `crates/cli/tests/fixtures/templates/perspectives/`: a
  template with three fixture perspectives (`fixture-a`, `-b`, `-c`),
  each a trivial stage, and one declared move `a → b`.
- **CI:** for the built-in template, make and build a game for every
  pair of ready perspectives. With one ready perspective, this job
  makes the fixture games instead, so it runs from day one.
- **Either order with 2771** (parked: the `stage-hex-grid` part): if
  2771 is done, `hex-grid` is a ready perspective with a part, so the
  job above makes and builds its pairs: check that they pass through
  the door. If not, nothing to do: 2771 checks its pairs when it lands
  (its clause says so).

**Out (do not do):**
- writing any perspective's stage part (each perspective ticket does:
  1122, 1126, 1127);
- writing a real move (1125 writes top-down free to grid);
- carrying game state beyond `Carry { from }`.

## Implementation steps

1. Add `moves` to `Part` and `ComposeError::SameMove`, with fixtures.
2. Generate `src/stages.rs`, the flow, the door and the `travel` action
   in the base part.
3. Generate the README section and `tests/moves.rs`.
4. Write the fixture template and the integration test.
5. Add the CI job.
6. Remove the "separate stages" `limits` entry 2502 added.

## Acceptance criteria

- [ ] A game made from the fixture template with `a,b,c` picked builds,
      and its generated `tests/moves.rs` passes: it crosses `a → b` by
      the declared move, `b → c` and `c → a` by doors.
- [ ] Picking one perspective gives no flow moves, no `travel` action,
      and no `tests/moves.rs`.
- [ ] `travel` appears in the generated keymap file and nowhere as a
      literal key in the generated code (a test greps the plan).
- [ ] Two parts declaring the same move fail with both parts named.
- [ ] The CI job runs on every PR.
- [ ] All gates in the `run-gates` skill pass.

## Tests required

- Unit: the pair walk (order, back to the first), `SameMove`.
- Integration: the fixture games for `a,b`, `a,b,c` and `c,a` build and
  pass their generated tests (CI).
